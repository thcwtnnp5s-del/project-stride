## 0. Headline findings

1. **The equipment seam already exists and is deliberately empty.** GFCP01
   shipped `EquipmentVisualState` (a derive-on-read projection, zero persisted
   state) and `TravelerArt` (three `const` tables, all empty, total fallback to
   the base strips). Two of five Traveler-drawing surfaces are wired through
   it. Nothing is architecturally blocked; only art is missing.
2. **The PixelLab balance is no longer 25.** `get_balance` returned
   **10,000 generations remaining, 0 used, Tier 3 "Pixel Architect", resets
   2026-10-01**. Every cost argument in GFCP01 §12 and `JOURNAL/OPEN_QUESTIONS`
   Q-14/Q-15 was written against a 25-generation reserve and is now obsolete.
   **Generations are not the constraint any more. Blind-QA capacity is.**
3. **Runtime overlay compositing on the *existing* art is not viable**, and I
   can now say why with numbers rather than assertion — see §7. The decisive
   measurement: in `traveler_combat_idle_f0.png` the blade region (x ≥ 56)
   contains 7 distinct colours and **0 of the 7 are exclusive to it** — every
   blade colour also occurs on the body. The baked tool cannot be removed, or
   recoloured, by any deterministic rule.
4. **Precomposed variants do not compose.** Three slots × ~5 coarse classes is
   a **product** (125 loadouts), not a sum. A "weapon strip" has an armour
   baked into it; an "armour strip" has a weapon baked into it. Full
   cross-product coverage of all 29 sequences is ~3,600 tracks and is not a
   thing anyone should build.
5. **The recommendation is precomposed with per-surface axis dominance**
   (§9) — the shape `TravelerArt` already has. It fits inside one cycle's
   generations, needs **zero save changes**, and reverts by emptying maps.
6. **Brace has no art.** `combat_choreography.dart:231-237` holds
   `traveler.idle` for 350 ms with the comment "no authored stance pose
   exists". The P0 brief's combat surfaces are one sequence short before any
   equipment work starts.

## 2. Canonical canvas, baseline and pivot — and where it is inconsistent

**Canonical:**

- **Height is universally 64.** No exceptions across all 29 sequences.
- **Baseline row 62** for 28 of 29 sequences. The figure occupies rows 0–62
  with one empty row below.
- **The nominal figure box is 64 × 64.** Wider canvases exist purely to give a
  swinging tool room: widths measured are **44, 46, 56, 60, 64, 74, 76, 80,
  96**.
- **Pivot is not a stored number — it is derived per sequence from the
  footprint.** `SpriteFootprint.centerX = (left + right + 1) / 2`
  (`lib/ui/icons/sprite_footprints.dart:35`). The south still's is 31.0.

**Two different placement conventions coexist:**

| Convention | Where | Rule |
|---|---|---|
| `anchorX` | ambient scenes | `anchorX = (canvas - 64) ~/ 2`, `ambient_scene.dart:376`; a wide frame is drawn shifted left by `anchorX` so the figure stands where the 64-box stands (`ambient_player.dart:637`) |
| footprint centre | combat stage | `left = offset + column*scale − round(footprint.centerX*scale)`, `combat_stage.dart:723-724` |

### Inconsistencies, precisely

1. **`gather` sits one pixel lower than everything else.** Its baseline is row
   **63**, footprint `bottom: 63` (`sprite_footprints.dart:47-51`), against 62
   everywhere else. It is also `AmbientAssets.restFrame`
   (`ambient_assets.dart:307`) — the pose both the Adventure stage
   (`location_stage.dart:163`) and the Craft stage (`craft_screen.dart:1053`)
   rest on. **The resting Traveler therefore stands 1 px lower than the ambient
   Traveler that replaces him**, and the contact shadow moves with him. Under
   any variant scheme this offset must be reproduced or corrected once,
   deliberately.
2. **The two conventions disagree by 2 px on the 80-wide combat frames.**
   `combat_assets.dart:43-45` records it: footprint centre 40 against
   `34 + anchorX(8) = 42`.
3. **Footprints are measured on frame 0 only.** `package-art.js` guards every
   footprint write with `if (i === 0)` (lines 456, 488, 502, 714, 750, 844).
   Measured consequence: `activity_forage` frames f2–f8 have their lowest
   opaque row at **61**, but the footprint says 62, so the contact shadow sits
   one row below the feet for 7 of the sequence's 9 frames.
4. **Footprint centres differ per work loop and none matches the 64-box.**
   woodcut 38.5, mine 34.5, smith 36.5, cook 27.5, forage 26.5, against the
   south still's 31.0. Runtime placement is by footprint so this is *coherent*,
   but there is **no single project-wide pivot column** to hang an overlay on.

### The public API surface

| Type | File:line | Role |
|---|---|---|
| `PixelAsset` | `lib/ui/components/pixel_asset.dart:45` | integer-scaled nearest-neighbour draw of one PNG; named ctors bind native size (`.sprite` = 64², `.portrait` = 64², `.item` = 48²) |
| `GroundedSprite` | `lib/ui/components/grounded_sprite.dart:79` | `{assetPath, footprint, scale=2, canvas=64, canvasHeight}` → a `Stack` of a `CustomPaint` contact shadow **under** a `PixelAsset`. **Every standalone figure must go through this** |

| `AmbientTrack` | `ambient_scene.dart:48` | `{frames: List<String>, fps, loop, repeats}`; `frameAt(Duration)` / `frameAtSustained(Duration)` (`:88`, `:107`) |
| `AmbientLayer` | `ambient_scene.dart:316` | **the existing layer-compositing primitive** — see below |
| `AmbientScene` | `ambient_scene.dart:360` | one Traveler track + `List<AmbientLayer>` + `anchorX` + phasing |
| `CombatTrack` | `lib/ui/icons/combat_assets.dart:83` | `{id, track, canvasWidth, canvasHeight, anchorRow, footprint}` |
| `CombatantArt` | `combat_assets.dart:116` | `{idle, attack, strikeFrame, heavy?, heavyStrikeFrame?, hit?, defeat?, stagger?, impactRise}` |
| `SpriteAnimation` | `lib/ui/components/sprite_animation.dart:34` | one-shot on `playToken`, rests on frame 0 |
| `TravelerArt` | `lib/ui/icons/traveler_art.dart:45` | **the equipment seam** — see §4 |

### How frames advance

Three independent clocks, all `AnimationController` + `addListener` +
`setState`, none of them a shared game loop:

- **Ambient:** `ambient_player.dart:600-608` `_onTick` recomputes
  `_framesAt(_elapsed)` — a `List<int>` whose element 0 is the Traveler frame
  and elements 1..n are the companion layers' frames
  (`ambient_player.dart:576`) — and `setState`s only when the vector changes.
- **Combat:** `combat_stage.dart:466-513` `_onTick` → `_refresh(elapsed)` →
  `_shotAt(elapsed)` builds a `_Shot` value carrying `travelerTrack`,
  `travelerFrame`, `enemyTrack`, `enemyFrame`, dx offsets, HP tweens and
  effects. `t.frameAt(elapsed - s.travelerStart)` at `:551`.
- **Gather one-shot:** `sprite_animation.dart:114-121`,
  `floor(controller.value * frames.length)`.

All three precache with `precacheImage(AssetImage(f), context)`
(`sprite_animation.dart:91`, `combat_stage.dart:280`,
`travel_transition.dart:84`).

### Existing layer-compositing capability — yes, it exists

`ambient_player.dart:645-673` is a real multi-layer compositor:

```dart
Widget layerAt(int i) => Positioned(
  left: (l.dx * scale).toDouble(),
  top:  (l.dy * scale).toDouble(),
  child: GroundedSprite(assetPath: l.track.frames[_frames[i + 1]],
                        footprint: l.footprint, scale: scale, canvas: l.canvas));
...
Stack(children: [
  for (...) if (s.layers[i].behind) layerAt(i),
  Positioned(top: 0, left: shift, child: traveler),
  for (...) if (!s.layers[i].behind) layerAt(i),
]);
```

Each layer has **its own independently-advancing track**, **its own footprint
and shadow**, an integer `(dx, dy)` in 64-box sprite pixels that scales with the
figure, and **one bit of z-order** (`behind`). It is used today for the orange
cat and the yarn/fire props.

**What it does not have, and what an equipment overlay needs:** the offset is
**per scene, not per frame**. `AmbientLayer.dx/dy` are `final int` on the
layer, read once (`:646-647`). A cat that sits still is served perfectly; a
sword in a hand that travels 13 px across a 4-frame swing is not.

### Sprite-sheet slicing

**None.** One PNG per frame; `_frames(id, n)` generates paths. No `centerSlice`,
no atlas, no `SpriteSheet` type. (`PixelFrame`, `pixel_asset.dart:315`, tiles a
nine-patch for *panels* and explicitly refuses `centerSlice`; it is unrelated to
characters.)

## 4. `EquipmentVisualState` — what GFCP01's "equipment seam" actually is

### The projection (`lib/runtime/stride_session.dart`)

```dart
final class EquippedVisualFact {            // :310
  final String itemId;                      // ContentId.value
  final int tier;                           // ItemDefinition.tier, 0 if absent
  final String toolKind;                    // ToolKind.name — 'axe'|'pickaxe'|'none'
}                                           // value-equal (:325-334)

final class EquipmentVisualState {          // :336
  final EquippedVisualFact? weapon;
  final EquippedVisualFact? armor;
  final EquippedVisualFact? tool;
  static const none = EquipmentVisualState();   // :344
}                                           // value-equal (:347-356)
```

**Where it comes from:** `StrideSession.equipmentVisualState`
(`stride_session.dart:4258-4285`) — a getter that reads
`engine.state.equipment.bySlot[slot]` for each of the three
`EquipmentSlot` values, looks the id up in `ContentRegistry.items`, and
returns. **Derived on read; stores nothing; caches nothing.** Returns
`EquipmentVisualState()` when engine or registry is null.

**Deliberately string-keyed** so the presentation layer names no `stride_core`
type — the same boundary `AmbientAssets.activityLoopFor` keeps.

### The resolver (`lib/ui/icons/traveler_art.dart`, 89 lines, whole file read)

Three `const`/`final` tables, **all three shipping empty**:

| Table | Line | Key → value | State today |
|---|---|---|---|
| `variantOfItem` | :61 | item id → coarse variant class (`'item.bronze_sword' → 'weapon.bronze'`) | `{}` |
| `combatVariants` | :68 | weapon class → `CombatantArt` | `{}` |
| `walkWestVariants` | :72 | armour class → `List<String>` (6-frame walk) | `{}` |

Two resolvers, both **total**:

```dart
static CombatantArt combatantFor(EquipmentVisualState v) =>       // :80
    combatVariants[_variantOf(v.weapon?.itemId)] ?? CombatAssets.traveler;
static List<String> walkWestFor(EquipmentVisualState v) =>        // :86
    walkWestVariants[_variantOf(v.armor?.itemId)] ?? travelerWalkWestFrames;
```

The file's own doc-comment (lines 32-39) records the runtime-overlay rejection
and its reasoning.

### What consumes it — 2 of 5 surfaces

| Surface | Wired? | Evidence |
|---|---|---|
| Combat stage | **yes** | `combat_screen.dart:201` passes `session.equipmentVisualState`; `combat_stage.dart:258` `_traveler = TravelerArt.combatantFor(widget.equipment)` (snapshot at encounter start, deliberate) |
| Travel transition card | **yes** | `atlas_selection_panel.dart:150` passes it; `travel_transition.dart:76` `TravelerArt.walkWestFor(equipment)` |
| Adventure ambient + gather stage | **no** | `location_stage.dart:151-179` calls `AmbientAssets.scenesFor` / `activityLoopFor` directly |
| Craft stage (smithing/cooking) | **no** | `craft_screen.dart:972, 1048-1060` likewise |
| Character screen portrait | **no** | `character_screen.dart:92` `PixelAsset.portrait(PixelIcons.portraitTraveler)` |

**So the seam exists, is honest, is tested, and covers two of the five places
the Traveler is drawn.** Extending it to the other three is pure plumbing —
`AmbientAssets`' three `*For(skill)` accessors already have exactly the right
shape to take a second `EquipmentVisualState` argument.

## 7. Layering feasibility — concrete assessment

### 7a. Is per-frame overlay compositing viable on the existing art? **No.**

Four independent blockers, each measured:

**(1) The figure is not rigid; there is no anchor to hang anything on.**
Per-frame opaque-box centres measured this audit:

| Track | per-frame `cx` | travel |
|---|---|---|
| `traveler_attack` (4f) | 36.5 → 41.0 → 49.5 → 40.0 | **13.0 px** |
| `traveler_combat_idle` (9f) | 47.5 … 49.5 | 2.0 px |
| `activity_woodcut` (8f) | 27.0 … 50.5 | **23.5 px** |
| `activity_smith` (7f) | 26.5 … 49.5 | **23.0 px** |
| `activity_mine` (8f) | 25.0 … 36.5 | 11.5 px |

The "2–3 px drift" risk the brief asks about is the *wrong* risk. The bbox
centre alone travels up to 23.5 px within a loop, and the **hand** travels
further and rotates. An overlay pinned to any static offset is not 2–3 px
wrong, it is tens of pixels wrong for most of every swing.

**(2) The anchor data does not exist and cannot be measured deterministically.**
The only per-sprite geometry in the repo is `SpriteFootprint` (ground contact,
`{left,right,bottom}`) and `SpriteBounds` (opaque box). Both are **edge**
measures. Neither locates a hand. `package-art.js` measures footprints only,
and only on frame 0 (`if (i === 0)`, six call sites). Producing 219 grip
anchors — position *and* rotation *and* z-order — is a per-frame creative
judgment about anatomy, which `RULES.md` A-1 assigns to PixelLab and A-2
excludes from "deterministic transformation".

**(3) The baked tool cannot be removed, and it cannot be recoloured.**
Measured on `traveler_combat_idle_f0.png`:

- 64 distinct RGB values in one frame; 73 across the four combat tracks' f0/f2.
  This is not an indexed ramp.
- The blade region x ≥ 56 contains **7** distinct colours
  (`132,154,145` ×18 · `206,208,185` ×15 · `68,101,154` ×10 · `104,134,157` ×3
  · `86,120,164` ×3 · `177,191,166` ×2 · `57,89,145` ×2).
- **0 of those 7 colours are exclusive to the blade region** — every one also
  occurs in x < 56 (the body).

Therefore: an overlay would **double-draw** (baked sword + overlay sword), and
the steel→bronze palette remap floated in Q-14 is **not deterministic** — it
would recolour body pixels too. It needs per-frame spatial masks, i.e.
authoring. This closes Q-14's sub-question with evidence rather than taste.

**(4) One z-bit is not enough.** `AmbientLayer.behind` is a single bool. A
blade passes *in front of* the torso at `traveler_attack_f2` (the extended
strike, opaque box reaching x = 72) and *behind* the near shoulder at
`combat_idle_f0`. Correct occlusion needs per-frame ordering, and in places
per-frame masking — again authoring.

### 7b. What would be needed to make layering work

A *new base body* with no gear baked in, plus, per frame, `{gripX, gripY,
rotationDeg, zOrder}` — 219 × 3 slots ≈ 660 anchor records — plus per-frame
occlusion masks wherever a limb crosses. **PixelLab cannot produce any of
that.** It generates whole figures; it exposes no skeleton, no rig, no
attachment point, no per-frame metadata. There is no API surface for it in the
MCP tool set.

### 7c. Does PixelLab support consistent equipment states on a shared base? **Yes — but as precomposition, not layering.**

The canonical Traveler is live and healthy:
`c82b7da5-cda0-44eb-ae4e-30d73689e115` — *"Stride Traveler —
PIXELLAB_PROOF_01"*, **64 × 64, 8 directions, low top-down, state "Idle",
group `eb569ca7-…`, 61 animation groups / 71 animations** (verified via
`get_character` this audit).

- **`create_character_state(character_id, edit_description, …)`** is *exactly*
  the equipment-variant primitive. Its own contract: *"keeps the source's
  identity, body type, and proportions, with the edit applied consistently
  across all 4 or 8 rotations… ALWAYS preserves the SAME individual's face and
  identity, even for edits like… a different class/role."* Examples given
  include **"wearing red armor"**.
  - `override_width` / `override_height` exist precisely for *"when the edit
    adds something big (a weapon, wings) needing room beyond the character's
    tight canvas"* — which is how an 80-wide combat state gets its blade room.
  - `use_color_palette_from_reference: true` snaps the new state to the source
    palette — the identity guard.
  - **Cost 20–40 generations** per state; returns a *new* `character_id`
    grouped by `group_id`.
- **`animate_character` v3** then rebuilds each track on that state. Cost is
  `ceil(w·h·frames/65536)` per direction: at 64 × 64 × 9 frames that is
  `ceil(36864/65536) = 1` generation per track. At 80 × 64 × 9 it is still 1.
  **Animation is essentially free at this project's canvas size.**
- `custom_start_frame_url` / `end_frame_url` allow pinning a track's first pose
  to an existing accepted frame — the technique PLAYABLE_POLISH_02 already used
  (*"v3, east, custom start = the raw attack's f3"*).

**The tool's native shape is precomposition.** It has no layering concept at
all.

## 9. Architecture recommendation

### **PRECOMPOSED, with per-surface axis dominance.** Reaffirm GFCP01's (B), and scope it by what each surface is *for*.

**Reasoning:**

1. **Layering is not merely expensive here, it is unpurchasable.** §7a
   establishes that the existing art has no anchors, cannot yield them
   deterministically, and has the tool baked in with a non-separable palette.
   §7b establishes PixelLab exposes no rig, attachment or per-frame metadata.
   The blocker is not budget — it is that nothing in the toolchain emits the
   data layering requires.
2. **`create_character_state` is purpose-built for this problem** and preserves
   identity across all rotations by contract — the one guarantee an equipment
   system needs and the one a hand-composited overlay cannot give.
3. **The cross product is the trap, and axis dominance is the escape.** Do not
   try to show all three slots everywhere. Vary **the slot that surface is
   about**, and hold the others at base:
   - **Combat** is about the weapon and the coat that keeps you alive → vary
     **weapon × armour** (20 loadouts × 4 tracks). This is the P0 promise:
     "Bronze Sword in hand" and "armour changes the silhouette", in the one
     place both are load-bearing (defence 9 wins the Oakback Bear at ~64 %
     health where defence 2 dies on turn 5).
   - **Work loops** are about the tool → vary **tool** on mine/woodcut (and
     the two inspect scenes), hold armour at base. This is the P0 promise
     "a pickaxe must appear during Mining".
   - **Walk / gather-rest / still / portrait** are about the silhouette →
     vary **armour** only.
   - **The 14 solo ambient scenes stay base, permanently.** They are idle
     flavour; 122 frames × 5 armour classes buys the least read per generation
     of anything on the list, and partial delivery already degrades gracefully
     per-sequence.
4. **The seam is already this shape.** `combatVariants` is keyed by weapon
   class; `walkWestVariants` by armour class. The change is *data plus one
   more table*, not an architecture.

### Save changes: **ZERO. This is a hard requirement and it is already met.**

- Equipment already persists as `Map<EquipmentSlot, ContentId>` —
  `game_state.dart:153-178` (`Equipment`), encoded by slot **name** in
  `save_codec.dart:175, 304-310, 1066-1069`.
- `equipmentVisualState` is a **getter** that reads that map and allocates
  value objects (`stride_session.dart:4258-4285`). It holds nothing, caches
  nothing, writes nothing — pinned by
  `test/equipment_visual_test.dart:108-121` *"reading the projection commits
  nothing"*.
- Variant classes live in **presentation-layer `const` maps**, not in content
  and not in `stride_core`. No content-pack field, no schema version, no
  migration. **State stays v9.**
- Revert is emptying the maps — byte-identical output, exactly as today, pinned
  by `equipment_visual_test.dart:77-106`.

### Risks to name up front

- **W1 changes what a fight looks like on an existing save.** It is
  presentation-only and reverts cleanly, but the owner should see it on device
  before it merges.
- **The `gather` 1-px baseline anomaly (§2.1) must be decided once**, not
  reproduced accidentally in 5 armour variants of the rest pose.
- **Frame-0-only footprints (§2.3)** will silently propagate the forage shadow
  defect into every variant. Fix or accept deliberately before generating.
- **A weapon variant that is not also an armour variant is an honest partial,
  not a lie** — the base tunic is a real thing the Traveler can wear. But a
  *bronze-armoured* player in W1–W3 will fight in a tunic. That is the price of
  axis dominance and the owner should agree to it before W1, or fund W4.
